# Development Plan

## 開発方針

まずはゲームの核となる「マップ上でユニットを選択し、移動し、攻撃し、ターンを切り替える」部分を完成させます。
その後、占領・収入・生産・AIを段階的に追加します。

## Phase 0: 企画と仕様整理

### 目的

実装前に、最小版のゲーム仕様と作業順を明確にします。

### タスク

- ゲーム概要を整理する
- ユニット仕様を整理する
- 地形仕様を整理する
- MVPの完成条件を定義する
- 今後の拡張候補を分離する

### 成果物

- `docs/GameDesign.md`
- `docs/UnitSpec.md`
- `docs/TerrainSpec.md`
- `docs/DevelopmentPlan.md`

## Phase 1: プロジェクト初期構築

### 目的

TypeScript + Phaser + Vite で開発できる土台を作ります。

### タスク

- Vite + TypeScriptプロジェクトを作成する
- Phaserを導入する
- Git管理対象と除外対象を整理する(`.gitignore` をNode向けに整備)
- Vitestを導入し、テストが実行できることを確認する
- ESLint / Prettierを設定する
- 基本シーン(Phaser Scene)を作成する
- 基本フォルダ構成を作る
- GitHub Pagesへのデプロイ(GitHub Actions)を設定する

### 推奨フォルダ構成

```text
src/
  core/      // ゲームロジック(描画非依存。ユニットテスト対象)
    ai/
    battle/
    economy/
    map/
    turn/
    units/
  data/      // ユニット・地形・マップのJSONデータ定義
  scenes/    // PhaserのScene(起動・マップ選択・メイン)
  ui/        // UI表示コンポーネント
  assets/    // スプライト・タイル・効果音
tests/       // Vitestによるロジックのテスト
```

### 設計方針

ゲームロジック(`src/core/`)はPhaserに依存させず、純粋なTypeScriptとして実装します。
これにより移動範囲計算・ダメージ計算・AIをブラウザなしでテストできます。

## Phase 4: 移動システム

### 目的

ユニットごとの移動力と地形移動コストに応じて移動できるようにします。

### タスク

- 地形別移動コストを実装する
- 移動可能範囲を計算する
- 移動可能範囲をハイライト表示する
- 移動先クリックでユニットを移動する
- 移動後に行動済み状態へ変更する
- 敵ユニットがいるマスを通過不可にする

### アルゴリズム

地形ごとの移動コストがあるため、移動範囲計算にはダイクストラ法を使います。

## Phase 9: 簡易AI

### 目的

敵軍が最低限の行動を取れるようにします。

### タスク

- 敵ユニット一覧を取得する
- 攻撃可能な敵がいる場合は攻撃する
- 攻撃できない場合は最寄りの敵に近づく
- 歩兵が占領可能な場合は占領する
- 資金があれば工場でユニットを生産する

### AI優先順位

1. 攻撃可能なら攻撃
2. 占領可能なら占領
3. 近くの敵へ移動
4. 生産可能なら生産
5. 何もできなければ待機

### サウンドの実装方針

音源はすべてオリジナルとするため、外部の音声ファイルを持たず **Web Audio API でファミコン風のチップチューンをコード生成** する。

- `src/audio/notes.ts`: 音名→周波数の変換(純粋ロジック。Vitestでテスト)
- `src/audio/soundDefinitions.ts`: 効果音・BGMの「楽譜データ」(純粋データ。コードから分離)
- `src/audio/SoundEngine.ts`: Web Audio を薄くラップした発音エンジン(トーン・ノイズ)
- `src/audio/SoundManager.ts`: 効果音再生・BGMループ・ミュートを統括する高レベルAPI

BGMは自軍テーマ(長調・行進曲風)と敵軍テーマ(短調・緊張感)を用意し、手番で切り替える。
ブラウザの自動再生制限に対応するため、AudioContextは初回のユーザー操作で起動する。
非対応環境(SSR・テスト等)では静かに無効化し、ゲーム進行に影響しない。

## リスクと対策

| リスク | 対策 |
|---|---|
| 最初から仕様を大きくしすぎる | MVPを小さく保つ |
| AI実装が難航する | まずはプレイヤー同士で動く状態を作る |
| バランス調整に時間がかかる | パラメータをJSONデータとして外部化し、調整しやすくする |
| 原作再現に寄りすぎる | 固有表現はオリジナル化する |
